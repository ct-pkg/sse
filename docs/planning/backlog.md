# 本仓待办与已决事项

> 只记录本仓自己的任务与决定：为什么需要、要做什么、等什么、怎么验收。
> 本文不改变契约与版本；未满足条件的事项保持阻塞。

## 1 待办：包清单补充发布者与命名根

**为什么需要**：消费方通过包管理器取包时，需要知道发布者和 import 的命名根。当前 `ct.pkg`
只有 `name`、`version`、`licence`、`requires`，取包方无法从清单里得到这两项信息。

**要做什么**：在 `ct.pkg` 增加 `publisher = ct` 与 `ns-root = .`；同步把 README 构建示例的
include 根改成包根。

**等什么**：包管理器能把包落到 store 并读出 `publisher`，且 `-I` 能按 `ns-root` 解析 `import`。
在这两个能力可用之前，改了也无法验证，只会把“未验证的清单字段”当成已完成。

**怎么验收**：
1. `ct.pkg` 含 `publisher` 与 `ns-root` 两个字段。
2. 取包后 store 能读到 `publisher`。
3. `-I` 按 `ns-root` 解析 `import`，消费方无需手写包内子目录。
4. `python3 tools/check_api.py` 退出 0（公开面不变）。

**当前状态**：阻塞。工作区已有未提交的 `ct.pkg` 与根 `README.md` 改动，内容正是这两项；
按“不提交、不丢弃”处理，等上述能力可用后统一验收并提交。

**本仓的分期判断**：不单独立 phase。它是包清单的配置补全，不新增解析能力、不改公开面；
能力可用后按“字段落地 → 消费方验证 → 提交”做一次小步推进即可，不需要独立卡与版本移动。

## 2 待办：发布 tag `v0.11.0`

**为什么需要**：`0.11.0` 已收口，需要一个与 `version` 一致的 annotated tag 作为发布点，
否则消费方无法按 tag 取到这一版。

**要做什么**：在默认分支可达的提交上创建 annotated tag `v0.11.0`。

**等什么**：第 1 项的包元数据先落地；tag 与 push 由 owner 执行。当前不在本仓授权内。

**怎么验收**：
1. `git cat-file -t v0.11.0` 输出 `tag`（annotated）。
2. `git branch --contains v0.11.0` 包含默认分支。
3. `grep '^version' ct.pkg` 为 `0.11.0`。
4. `git describe --tags --exact-match` 输出 `v0.11.0`。

**当前状态**：阻塞，未创建 `v0.11.0`；仓库现有 `backup/pre-s4-rollback` 是备份 tag，
不是发布 tag。

**本仓的分期判断**：不单独立 phase。它是发版动作，不是能力片；等第 1 项验收后，
按“确认版本 → 打 annotated tag → 校验可达与一致性 → owner 推送”一次做完。

## 3 已决：构造形态保持自由函数

**背景**：类型工厂（把构造挂在类型上）曾是候选形态；当前公开契约已冻结为自由函数
`sse_parser_new()`，代码、示例与夹具都按这个形态落地。

**决定**：不回退为类型工厂。

**理由**：
1. 构造形态已经写进冻结契约，切换会改变公开面、示例与全部夹具。
2. 类型工厂不带来功能收益；它只是另一种写法，不是缺陷修复。
3. 若未来确实需要类型工厂门面，应作为新需求与新 phase 评估，而不是回退既有契约。

**验收**：`grep -rn "SseParser::new" sse test README.md` 为 0；`tools/api_surface.txt` 不变；
`python3 tools/check_api.py` 退出 0。

**本仓的分期判断**：已完成，不立 phase。结论本身是设计决定，不需要新代码；若以后要做类型工厂门面，
那是新需求，届时再按新的能力片评估。

## 4 需要 owner 拍板

1. 第 1 项的两个包管理器能力可用后，是否立即提交清单改动并接着做第 2 项；tag 与 push 由谁执行。
2. 第 3 项“保持自由函数”的决定是否接受；若要求类型工厂门面，另立需求与 phase 卡。
3. 工作区里那批未提交的 `ct.pkg`/`README.md` 改动由谁、在什么时点提交；本仓不擅自提交或回退。
